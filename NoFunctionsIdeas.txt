Best alternatives to Azure Functions
1. Best fit: .NET Worker Service on Azure Container Apps
Use 1-3 worker services instead of many functions.
•	Coordinator worker starts a scrape and enqueues work
•	ProductWorker consumes product jobs
•	InventoryWorker consumes inventory/store jobs
This keeps the same queue-based design, but removes Azure Functions entirely.
Why it fits this codebase
•	Program.cs already wires SDK clients and DI directly.
•	IImportingService already contains the real work.
•	The function methods are thin wrappers around queue messages.
Why it avoids the old problem
•	No single long-running request/function.
•	Work stays chunked and resumable.
•	Container Apps is a better host for always-on workers than App Service background tasks.
2. Azure Container Apps Jobs for full scrape runs
If scraping is more batch-oriented than always-on:
•	one job starts on schedule or manual trigger
•	it processes a bounded batch
•	it checkpoints progress in SQL/queue/blob
•	another job instance can resume later
This is a good replacement for the old “one long process,” but without depending on App Service lifetime behavior.
3. Fewer services, but still message-driven
Instead of many tiny functions, collapse into one worker service with internal handlers:
•	one queue
•	message type per stage
•	one BackgroundService
•	bounded concurrency with Channel, SemaphoreSlim, or queue polling
That gives a simpler deployment model while keeping short, restartable units of work.
Recommended shape
Use:
•	.NET Worker Service
•	Azure Container Apps
•	Azure Service Bus or Azure Storage Queues
•	SQL for durable state/checkpointing
•	Blob storage only if raw payload retention is still useful
If the pipeline matters more than raw throughput, Service Bus is usually nicer than Storage Queues because of:
•	dead-lettering
•	retry behavior
•	duplicate detection options
•	better operational visibility
What to avoid
Avoid App Service + BackgroundService
If the concern is “background work may be cut off,” App Service is not the ideal host.
Avoid returning to one giant scraper loop
That recreates the original failure mode:
•	harder restarts
•	bigger retry scope
•	longer recovery time
•	more fragile deployments
Lowest-friction migration path
Keep IImportingService and move only the triggers/hosting:
1.	Replace each function trigger with a queue consumer in a worker service.
2.	Keep the current stage boundaries.
3.	Optionally merge Products + Inventories into one worker executable.
4.	Run it in Azure Container Apps.

Best overall:
A small set of .NET 9 worker services on Azure Container Apps, using queues and durable checkpoints.
That gives:

What Azure Container Apps Jobs gives you
A job is a container that starts, runs, and exits.
It can be triggered by:
•	schedule
•	manual execution
•	event trigger in some patterns
That means it matches a scraper run much better than an always-on app.
Good ways to structure it
Option 2A: One job that runs the entire scrape with checkpointing
Use one container app job that:
1.	starts a scrape run
2.	gets product IDs
3.	processes them in batches with bounded parallelism
4.	writes progress to SQL
5.	exits when done
This is the simplest deployment model.
Use this if:
•	one scrape can complete within the job timeout you choose
•	the site is stable enough
•	you want fewer moving parts
Important: do not make it one giant in-memory process.
Make it resumable by persisting:
•	scrape run ID
•	current stage
•	completed product IDs
•	discovered store IDs
•	retry counts
•	timestamps/status
Then if the job is stopped, the next run resumes.
Option 2B: Multiple jobs by stage
Use separate jobs for:
•	SeedProductsJob
•	ProcessProductsJob
•	ProcessInventoriesJob
•	ProcessStoresJob
•	FinalizeJob
These can all be manually run or scheduled in sequence, or kicked off by a small coordinator.
Use this if:
•	the scrape is large
•	stages have very different runtimes
•	you want easier reruns of only one failed stage
This is closer to your current Azure Functions design, but with fewer Azure Functions-specific constraints.

How to make it safe
1. Add a ScrapeRun table
Track each run:
•	RunId
•	StartedUtc
•	CompletedUtc
•	Status
•	TriggerType
•	ErrorMessage
2. Add per-item work tracking
For example:
•	RunProducts with ProductId, Stage, Status, AttemptCount
•	or reuse incoming tables with run-scoped columns
3. Make every step idempotent
Each stage should be safe to rerun.
You already partly do this:
•	deduping stores via AddIncomingStoreIdsAndReturnAddedIds(...) in ImportingService.cs:108
•	DB retries are already configured in your host setup
4. Use bounded concurrency
Do not fan out unbounded HTTP requests.
Use something like:
•	Parallel.ForEachAsync
•	SemaphoreSlim
•	channels
This keeps the scraper polite and predictable.
5. Use a timeout larger than a typical run
Container Apps Jobs let you treat the scraper as a bounded batch process instead of a request/trigger function.

Two practical execution models
Model A: single-process pipeline
One job instance runs all stages.
Pros:
•	simplest
•	easiest to debug
•	least Azure plumbing
Cons:
•	less parallel scale-out
•	run duration may become large
Model B: job with internal batching and resume
One job instance still owns the run, but processes products in chunks:
•	load next 100 pending products
•	process with concurrency 8
•	save progress
•	repeat
Pros:
•	still simple
•	very resilient
•	easier to resume after interruption
Cons:
•	a bit more DB coordination logic
For your case, Model B is likely the sweet spot.

Scheduling and manual triggering
Container Apps Jobs support both scenarios well:
•	scheduled: cron-like schedule
•	manual: run on demand from portal/CLI/pipeline
That matches your requirement exactly.
A typical use would be:

Operational advantages over Functions for this scenario
•	easier mental model: “run container, do batch, exit”
•	fewer tiny deployment units
•	no function trigger plumbing
•	simpler local debugging
•	better fit for one-off or scheduled workloads
Tradeoffs
Pros
•	not always on
•	not tied to App Service background service lifetime
•	easier to reason about batch completion
•	can reuse most domain/service code
Cons
•	you must own checkpointing/resume logic
•	scaling is less automatic than tiny trigger-driven functions
•	observability/job history needs to be designed
My recommendation
For this codebase, use:
•	one Azure Container Apps Job
•	implemented as a .NET 9 Worker Service
•	with a BackgroundService
•	with SQL-backed checkpointing
•	with bounded concurrency
•	optionally keep blobs only for raw payload archival
If later a single job becomes too slow, split by stage into multiple jobs.
